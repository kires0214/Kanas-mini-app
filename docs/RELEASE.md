Реальные поля, цены, банковские ссылки и персональные данные в репозитории отсутствуют.

## Railway

Проект: **simple-field-management**, ID `9136df7c-c1e5-4315-b350-cf9f347056da`.
TEST: `1b6b4ab6-adc6-4ae4-abf0-61e1ef0d0815`.
Приложение: `kanas-app`, ID `c71d5772-62d8-42eb-a2d6-6230071a00a8`.
PostgreSQL: `Postgres`, ID `837e6ed8-13a0-4741-96e4-f30ec2bf1739`.

TEST уже развёрнут: https://kanas-app-test.up.railway.app. Фактические результаты — в [QA.md](QA.md).
DEV — локальная рабочая ветка; TEST — отдельное окружение Railway. PROD создаётся отдельно после
разрешения владельца, чтобы до запуска не держать лишние сервисы и не копировать тестовые данные.

Два сервиса: Next.js и PostgreSQL 18. Отдельный бот-сервер, Redis, cron и дополнительные платформы не нужны.
TEST не должен использовать production-токен, базу, клиентские данные или банковскую ссылку.
Не дублируйте TEST с тестовыми записями в PROD. Production-деплой требует отдельного разрешения владельца.

Приложение получает `DATABASE_URL=${{Postgres.DATABASE_URL}}` через приватную сеть Railway.
Публичный TCP-доступ к БД не требуется. `railway.json` задаёт сборку, миграцию перед запуском,
healthcheck `/api/health` и ограниченный перезапуск. Railway сам передаёт `PORT`.
Сервис приложения допускает sleep; отдельные дополнительные окружения можно держать пустыми до необходимости.

Переменные приложения:

| Переменная | Значение / назначение |
| --- | --- |
| `DATABASE_URL` | Ссылка на `Postgres.DATABASE_URL` в том же окружении |
| `TELEGRAM_BOT_TOKEN` | Секрет отдельного TEST-бота; для PROD — другой секрет |
| `ADMIN_TELEGRAM_IDS` | Реальные числовые Telegram ID администраторов через запятую |
| `KASPI_PAYMENT_URL` | Только выданная владельцем HTTPS-ссылка; до её настройки приём броней закрыт |
| `NODE_ENV` | `production`, в том числе для production-сборки в TEST |
| `NEXT_TELEMETRY_DISABLED` | `1` |
| `TZ` | `Asia/Almaty`; расчёты брони дополнительно явно задают эту зону в SQL |

Секреты вводятся в Railway Variables, никогда в Git или сообщения PR.
Не устанавливайте фиктивный платёжный URL в работающем клиентском приложении.
`.invalid` URL и синтетические пользователи используются исключительно в изолированном QA.

## Миграции

`npm ci`, затем `npm run db:migrate` при заданном `DATABASE_URL`.
Runner хранит `schema_migrations`, применяет каждый файл в транзакции и использует advisory lock,
чтобы параллельные деплои не применили миграцию дважды. Повторный запуск безопасен.
Уже установленная исходная `001_initial.sql` поддерживается: существующее exclusion-ограничение
не создаётся повторно. Перед обновлением существующей базы сделайте проверенную резервную копию.
В Railway миграция запускается `preDeployCommand`; при ошибке запуск новой версии прекращается.
Healthcheck требует актуальную миграцию `002_payment_safety.sql`.

## Telegram

В BotFather создайте отдельного TEST-бота и задайте HTTPS URL через `/setmenubutton`.
Пользователь и администратор должны нажать Start, иначе бот может не иметь права отправить им сообщение.
Внешний webhook для этого MVP не нужен: аутентификация Mini App и исходящие сообщения обслуживаются Next.js.
Сервер проверяет HMAC `initData`, единственность параметров, ID пользователя и срок действия (24 часа;
не более 60 секунд в будущем). При истечении нужно закрыть и заново открыть Mini App.
Неподписанные данные клиента и `initDataUnsafe` не являются источником полномочий.

## Платежи и спорные ситуации

- `held`: слот удерживается 20 минут. Истечение проверяется по времени PostgreSQL; неоплаченный слот освобождается.
- `review`: клиент сообщил об оплате. Это **не** подтверждение денег; слот не освобождается автоматически.
- `disputed`: администратор уточняет платёж; слот также остаётся занят до ручного решения.
- `confirmed`: администратор лично сверил поступление и сумму в Kaspi Pay.
- `rejected`: администратор записал причину и порядок решения вопроса. При возможном платеже сначала
  уточните деньги и согласуйте возврат; до этого используйте `disputed`.
- `expired` + `payment_issue_open`: клиент сообщил о платеже после окончания удержания. Обращение
  сохраняется в очереди без захвата чужой брони. Администратор проверяет деньги, согласует возврат
  или другое время, затем записывает решение. Автоматически подтверждать такой слот нельзя.

Очередь не скрывает неопределённые платежи после даты матча; проверки дольше 24 часов выделены.
Решения сохраняются в `booking_decisions`; финальное решение повторным противоположным запросом не меняется.
После изменения цены старые брони сохраняют снимок своей цены. Скрытие поля не отменяет оплаченные брони.

## Уведомления и восстановление

Сообщения администратору об оплате и клиенту о решении записываются в outbox в одной транзакции
с изменением брони. После commit приложение пытается отправить до трёх сообщений.
Сбой Telegram не отменяет решение и не удаляет сообщение. В админке виден остаток очереди
и есть кнопка повторной отправки (интервал повторной попытки — одна минута).
Отдельного фонового сервиса нет: если трафика нет, администратор должен открыть очередь и повторить отправку.
Telegram не предоставляет idempotency key для sendMessage, поэтому после аварии между отправкой
и фиксацией доставки возможен повтор уведомления. Источник состояния — база и «Мои брони».

При сетевом сбое клиент не повторяет изменение автоматически. Бронь имеет UUID `request_id`,
сохранённый на время неопределённого запроса в sessionStorage; повтор не создаёт вторую бронь.
Повтор отметки оплаты и того же решения администратора также безопасен.
Обновление вкладки, возврат из оплаты, восстановление сети и периодическое обновление перечитывают состояние.

## QA и допуск

Один GitHub Actions job использует PostgreSQL 18 и выполняет:

1. `npm ci` и `npm run typecheck`.
2. `npm test`.
3. `npm run test:integration`: настоящие SQL, транзакции, ACL, гонка 12 клиентов,
   соседние часы, прямое нарушение exclusion, истечение, повторы, лимит пользователя,
   review/dispute/late payment, подтверждение/отклонение и сбои Telegram.
4. `npm run build`.
5. `npm run test:e2e`: production HTTP-процесс → API → PostgreSQL → состояние клиента.
   Транспорт Telegram в этих автоматических тестах подменён; серверная авторизация работает с подписанными fixtures.

Integration/HTTP QA отказываются работать, если имя БД не начинается с `kanas_test`.
Fixtures не являются реальными коммерческими данными. Тестовый HTTP-процесс завершает свой child handle
и проверяет освобождение порта; сервис PostgreSQL удаляется вместе с CI runner.

До клиентов остаётся ручная проверка внутри настоящего Telegram с TEST-ботом:
открытие меню, auth, мобильная вёрстка, создание реального тестового поля владельцем,
переход по предоставленной TEST-платёжной ссылке, возврат в Mini App, ручное решение и фактическая доставка сообщений.
После этого — отдельное разрешение на PROD, production-переменные, резервное копирование и согласованный
контакт для спорных платежей. Банк автоматически не интегрируется.

## Остановка и ответственность

Railway-проект, приложение, БД и том — передаваемые владельцу ресурсы, необходимые для продолжения.
Они не являются временными локальными процессами. Чтобы остановить расходы, владелец проверяет точные
project/environment/service IDs и удаляет/останавливает нужный deployment в Railway Dashboard;
том с данными сохраняется отдельно. Не удалять production-данные ради очистки TEST.
Локальные серверы и Docker/WSL для этой работы не требуются.
